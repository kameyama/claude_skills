# review-lens

**差分の正しさではなく、マージ後に誰が何に困るかを見る。**

過去のレビューで kameyama は、一般的な観点での指摘を受け取ったあとに同じ種類の問いを重ねてきた。
また kameyama の PR は、同じ種類の指摘を繰り返し受けてきた。
このスキルは、その問いと指摘を先回りして答えるためにある。

## 呼ばれ方

- **explain-pr から**: Step 5（レビュー）で、一般的な観点の表を当てたあとに読む。材料は explain-pr が集めたもの（`pr.json`・`diff.patch`・`issue-N.json`・`base/`）をそのまま使う
- **単独で**: explain-pr の Step 1 と同じスクリプトで材料を集める

```bash
bash ~/.claude/skills/explain-pr/scripts/fetch_pr.sh <PR URL>
```

## 着眼点

12 個を順に当てる。PR に当てはまらない着眼点は飛ばす。当てはめたが問題がなかったものは、1 行で「確認した」と書く。

### 1. 顧客からどう見えるか

- 提供面・通知・顧客向けの資料は、変更の前後でどう変わるか
- 途中の状態（一部だけ着地した、途中まで更新した）は、顧客にどう見えるか
- 顧客にすでに出した資料や回答と食い違わないか。直近の Issue で顧客に答えた内容とあわせて読み、説明が二転三転して見えないか
- 技術仕様だけが確定して、顧客向けの依頼書・資料が古いままになっていないか
- 顧客に渡す値が**顧客の座標**になっているか。内部の座標（hive パスのキー、run_id、内部イベントの生の行）を渡して、畳み込みや日付の写像を顧客に再実装させていないか
- 顧客が受け取って**行動できる**ものだけを出しているか。出した項目は契約面になり、後から消せない
- 「完了」「最新」のような言葉が、どの層の事象を指すか（上流の取得完了・取込の完走・顧客から見える）。顧客に意味があるのはどれか
- 顧客に見える文（BigQuery の列 description など）が、列名の繰り返しや英語キーの機械的な結合になっていないか
- 移植元から引き継いだ名前・型が他と揃っていないとき、顧客の意図か、移植元や上流システムの実装都合が残っただけかを切り分けたか。直すなら作り直しが前提のタイミングが最も安い

### 2. シナリオごとに何が起きるか

- 状態・種別・ステータスを表す値は**すべて挙げて**、値ごとの違いを表にする
- 時系列のシナリオ（期限の到来、部分着地のあとの完了、再実行、切替の on / off をまたぐ run など）ごとに、何が起き、どの通知が誰に届くかを表にする
- 受け手が通知だけを見て状況を判断できるか。判断に別テーブルを引き直す必要があるなら、指摘の候補にする
- 配信の保証（at-least-once による重複、逆順の到着、保持期間を過ぎた欠落）ごとに、受け手が何をしなければならないかを書く。欠落に気づく手段がポーリングしかないなら、受け手の運用物は減っていない

### 3. 人の手順を仕組みで強制できるか

- 「人間の完了条件」「〜の plan は apply しない」のような人が守るルールを探す
- **そのルールはリポジトリのどこに残るか。** Issue と PR 説明にしか書かれていないなら、マージ後に次の担当者の目に入らない
- 仕組みで強制できないかを検討する（terraform の `lifecycle`、CI のジョブ、検査スクリプト、Claude Code のフック）。できるなら強制するほうを推す
- 強制するときの代償（意図した変更の手間）と、既に決まった判断を覆すかどうかを添える。代償には**他のメンバーの作業への影響**を含める（例: `ask` にすると、今まで止まらなかったエージェントの作業が毎回止まる）
- 逆に、規約・ルールを**足す**差分には、既存の判断基準で防げなかったかを先に問う。防げたなら足さない。問題のたびに規約を足すと、判断基準そのものが効かなくなる

### 4. 決定の変更か、誤りの修正か

ADR や設計書を書き換える差分に当てる。

- 下流（実装量、顧客向けの資料、運用手順）が変わるなら**決定の変更**。既存の ADR を書き直さず、新しい番号の ADR で置き換え、PR も分けるよう提案する
- 誤字や、明らかな事実誤りの訂正で下流が変わらないなら、既存の ADR を直してよい
- どちらに当たるかを、根拠と一緒に書く。書き換えた人が「誤りの修正」と主張していても、下流が変わるかで判断する

### 5. 兄弟 PR・環境との違い

- 積んだ PR や同じ型の PR（stg と prd、テナント A と B）があるなら、差分を比べて**コピーでない違い**を挙げる
- 違いが値だけなのか、構造や手順も違うのかを書く。本質的な違いが無いなら、そう書く
- 先の PR の変更が後の PR に手で波及しないか
- 同じ PR の中に同じ型のファイルが並ぶなら（データタイプごとの契約・モデル・テスト）、それらの間で揃っていない点を表にする（PK の順序、`required`、quality チェック、unit test の有無、列順、閾値のコメント）。1 本だけ欠けているものは写し漏れを疑う

### 6. 言葉の正確さ

- 用語が実体と合っているか（例: 列ではなく接頭辞なら「`_meta_*` 列」「`_meta_` 接頭辞の列」）
- 規約・手順の文面が一意に読めるか。想定されるパターンを挙げ、どのパターンでも「どこに・何を書くか」が文面から決まるかを確かめる
- コメントが述べる効く範囲（どの環境、どのテナント）が、コードの実際の範囲と一致するか
- コメント・docstring が述べる**主体**（誰がその値を付ける・返す・変換する）が正しいか。主体を誤ると、関係ない箇所にも処理が要るように読める
- 1 つの根拠を複数の利用者で共有しているなら、その根拠がすべての利用者に当てはまるか

### 7. 検査が走り、退行を捕まえるか

- 追加・変更したテストや quality・検査スクリプトが、本番のランナーや CI のどの経路で実行されるかを追う（selector、ワークフローの paths、呼び出し元）
- どの経路にも乗らないなら、説明に書かれた目的は果たされない。そのことを指摘する
- 走るテストについては、**守りたい性質を壊したら赤くなるか**を確かめる。たとえば次のものは緑のまま通る
  - fixture の値が全行同じで、キーから列を落としても区別が付かない
  - 比べる列が 2 つの run で同値で、勝者を取り違えても等式が成り立つ
  - 表だけを照合して、処理の順序や手順は照合していない
  - 正規化は通すのに、その後の再帰や検査の対象には入っていない表記がある
- 型の宣言や規約の方針が、実際に返る値・実装の判断軸と一致するか。`Any` から来た値に付けた戻り型は検査されていない。方針と実装の軸がずれると、同じ列で 2 つのルールが衝突する
- 守るための処理（マスク、フィルタ）が、実際に何を守っているか。守るものが薄いなら、代わりに失う情報のほうを指摘する

### 8. 事実の置き場所

- 同じ事実が 2 箇所以上に書かれていないか（設計書と仕様書、契約と SQL、テンプレートとスキル、元ファイルと生成したバイナリ）。正本を 1 つ決めて、他は参照にするよう提案する
- テナント共通の文書にテナント固有の内容が入っていないか。入っているなら、そのテナントの文書へ移す
- その情報が置かれた層の役割に合うか（例: 上流の受け渡し形式を公開用の契約に置かない、運用の都合を顧客向け description に書かない、選定理由を要件文書に置かない）
- コードや契約が増減すれば嘘になる数（件数・行数・列数）を書いていないか。列挙から分かる数は書かない。数の根拠は PR 説明に留める
- CLAUDE.md・スキルのように毎回コンテキストに乗る文書では、その文が読み手（AI）の行動を変えるか。変えない背景解説、エージェントにさせないことの記述、「〜ではない」の否定文、他の場所に正本がある知識は削るよう提案する。ディレクトリ固有の知識はルートではなくそのディレクトリに置く

### 9. 失敗したとき何が起きるか

- 設定の欠落・宣言の不一致・前提の崩れを**黙って通していないか**（未設定なら何もしない、キーが無ければ除外する、同名キーを片方で上書きする）。原因の位置で落とすか、少なくとも WARN 以上で残すよう提案する
- 1 件の異常が、関係ない範囲まで止めないか（ページ跨ぎの重複 1 件で 提供面全体の build が止まる）。止めるべきもの（gate）と通知で足りるもの（quality）を分ける
- 失敗を「ログだけ」で済ませるとき、その失敗で困るのが誰かを確かめる。困るのが顧客なら、後始末（アラート、再送、未送分の検出）が要る
- 2 つの書き込み（状態の記録と通知など）の片方だけが成功したときの後始末があるか

### 10. 前提が事実か

- PR の Before・課題として書かれた事実を確かめる（ログ、実績、設定）。前提が崩れれば、変更そのものが要らなくなる
- 課題と解決したいことが PR から読み取れるか。読み取れないなら、それ自体を問う
- 差分から読み取れる**作者のシステム像**を書き出し、README・CLAUDE.md・設計書の構造と照らす。ずれやすいのは次の点
  - テナントの非対称（片方のテナントの要件を共通の文書・モジュールに置いていないか）
  - 名前や型の正本（データ契約か、ビルドツールの生成物か）
  - 書き手は誰か（脇役と見た側も書き手なら、その手順と設定も更新が要る）
- 要件を書く差分には次を当てる
  - 要件が手段ではなく結果で書かれているか。手段を Must の本文に入れると、別解が最初から排除される
  - 設計を左右する数字（遅延の上限など）を顧客に確かめたか
  - 依存先の優先度が依存元より低くないか（Must が Should を前提にしている）
  - 顧客の WANT・条件付きの要望が、Must と同じ強さで書かれていないか

### 11. PR の範囲

- 性質の違う変更（基盤・ハーネスの修正と機能の実装、docs と他のコード）が混ざっていないか。分ければ先にマージできる部分があるなら、PR スタックの形を示して分割を提案する
- 同じ型の実装を何本も 1 つの PR に積んでいないか。最初の 1 本で拾える問題が残り全部に波及する
- 履歴にマージコミットや「追加→訂正」「追加→削除」のコミットが積まれていないか

### 12. 指摘の強さを確かめる

指摘を出す前に、自分の指摘に当てる。

- 実害を確かめたか。ローカルで試せるなら試し、CI のログが見られるなら見る（例: 並列化で `-s` の print が見えなくなるという指摘は、ログの出方を確かめてから書く）
- 「この PR で起きるようになる」と「前から起きていた」を分ける。前からあるなら「PR の範囲外」と書く
- PR が Issue どおりに書かれていて、ずれが Issue 側にあるなら、そう書き分ける
- 確かめられなかったものは推測と書く。言い過ぎるよりは弱く書く

## 出力

explain-pr から呼ばれたときは、別の節を立てない。

- 指摘は explain-pr の「コードレビュー」に混ぜ、先頭に `【着眼点 N: 見出し】` を付ける（例: `【着眼点 3: 人の手順を仕組みで強制できるか】`）。番号だけでは読み手が何の着眼点か分からないため、見出しは上の `### N.` の文言をそのまま使う
- 着眼点 1・2・5 で作った表（顧客からの見え方、シナリオごとの挙動、兄弟 PR との違い）は、「何がどう変わったか」の後ろに置く
- 着眼点 3・4・10 で判断が要るものは、「レビューで見るべきポイント」の上位に置く

単独で呼ばれたときは、着眼点ごとに見出しを立てて同じ内容を出す。

## 注意

- 着眼点を当てるために指摘をひねり出さない。当てはまらなければ飛ばす
- 選択肢を並べるときは、推す案を 1 つ明示する
- PR への投稿は post-pr-review が扱う。このスキルでは投稿しない
