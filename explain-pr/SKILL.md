# explain-pr

**PR を「差分」ではなく「機能の変化」として理解し、PR 説明を鵜呑みにしないレビューを返す。**

解く問題はひとつ。PR の差分だけを読むと、その行が何のためにあるのか分からず、
PR 説明に書いてあることの確認しかできない。レビューの価値は説明に**書いていない実害**を見つけることにある。

**GitHub には 1 バイトも書かない。** レビューコメントの投稿は別途ユーザーが行う。

## 方針: KISS

レビューの目的は、PR をシンプルで明確に保つこと。指摘の数を増やすことではない。

指摘は 2 段階で作る。**洗い出し**では観点をすべて当てて候補を出し切る。**取捨選択**では候補ごとに KISS で判断し、残すか落とすかを決める。洗い出しの段階で絞らない。

残す基準:

- 直さずマージすると誰が何に困るかを 1 文で言える
- 提案が今の実装より単純になる。層・設定・抽象・仕組みを**足す**提案は、無いと実害が出るときだけ残す
- PR 自体の過剰な構造（単一用途の抽象化、使われない柔軟性、将来のための設定・分岐）を削る提案は残す

落とした候補は書かない。残るものが無ければ「問題なし」と書く。

## 使い方

```
/explain-pr https://github.com/OWNER/REPO/pull/123
/explain-pr OWNER/REPO#123
```

## 処理フロー

### Step 1: 材料を集める

```bash
bash ~/.claude/skills/explain-pr/scripts/fetch_pr.sh <PR URL>
```

出力先ディレクトリが最後の行に出る。中身は `pr.json`（本体）、`diff.patch`、`review_comments.json`、
`issue-N.json`（紐づく Issue）、`base/`（変更ファイルの base 側全文）、`history/`（変更ファイルの直近コミット）。

サンドボックスで `gh` のネットワークが落ちたら、その旨を伝えて止まる。推測で埋めない。

### Step 2: 大元の機能を把握する（差分より先に読む）

`base/` の全文を読み、**変更前の**機能を理解する。差分を先に読むと差分の説明しかできなくなる。

- この機能は何のためにあるか。誰が（どのジョブ・エンドポイント・CLI が）呼ぶか
- 入力は何で、出力は何か。データがどこから来てどこへ行くか
- 変更対象の関数・クラスの責務はどこまでか

ローカルにチェックアウトがあれば（`ls ~/projects/<repo>`）呼び出し元を grep して影響範囲を広げる。
無ければ `gh api repos/OWNER/REPO/contents/<path>?ref=<baseRefOid>` で必要なファイルを追加で読む。
呼び出し元を確認せずに「影響なし」と書かない。

### Step 3: 背景を組み立てる

`pr.json` の body、`issue-N.json`、`commits`、`history/` を読む。

- **なぜ今この変更か**: Issue の動機、直前の関連コミット、PR 説明の課題記述
- **どんな経緯の上にあるか**: `history/` で同じファイルが最近どう動いてきたか
- **事実と推測を分ける**: Issue や説明に書いてあることは事実、そこから読み取ったことは推測と明示する

### Step 4: 差分を読む

`diff.patch` をファイル・関数単位で **Before → After** に整理する。行の変化ではなく**振る舞いの変化**を書く。

- PR 説明にある変更が実装に**ある**か
- PR 説明に**ない**変更が実装にあるか（副産物、リファクタ、便乗変更）
- テストは追加・変更されたか。変更した振る舞いをテストが実際に通過するか

### Step 5: 指摘の候補を洗い出す

Step 2 で理解した機能と Step 4 の差分を突き合わせる。PR 説明にない観点も含めてすべて当て、候補はこの段階で絞らない。観点一覧:

| 観点 | 見るところ |
|---|---|
| 正しさ | 境界値、null/空、エラー経路、例外の握りつぶし、並行実行 |
| 説明との乖離 | 説明にあるのに無い変更、無いのにある変更 |
| 影響範囲 | 呼び出し元、共有モジュール、公開 API・スキーマ・設定・データ形式の互換性 |
| データ | スキーマ変更、マイグレーション、冪等性、再実行、既存データとの整合、パーティション |
| テスト | 変更した振る舞いをカバーしているか、テストだけ通るように緩めていないか |
| 運用 | ログ、監視、ロールバック手順、フラグ、デプロイ順序の依存 |
| セキュリティ・権限 | 入力検証、認可、秘匿情報、IAM |
| 性能 | N+1、フルスキャン、メモリ、リトライの重複 |
| シンプルさ | 単一用途の抽象化、使われない柔軟性、将来のための設定・分岐、同じことを 2 通りで書いている箇所。削る提案にする |

続けて `~/.claude/skills/review-lens/SKILL.md` を読み、着眼点 1〜11 を当てて候補を足す。出力への混ぜ方も review-lens に従う。

### Step 6: 取捨選択する

候補ごとに「方針: KISS」の残す基準と review-lens の着眼点 12 を当て、残すか落とすかを決める。

残した指摘は **重要度 + 場所 + 理由 + 提案** の 4 点で書く。場所は `path:line`。理由のない指摘は書かない。

| 重要度 | 基準 |
|---|---|
| must | 直さずマージすると、顧客・運用者・データに実害が出る |
| should | 直さないと、次に読む人・直す人が誤解するか、同じ問題を繰り返す |
| nit | 好み。残す基準を満たしても原則落とす |

must は絞らない。should は 5 件まで、nit は 2 件までとし、重要なものから並べる。

### Step 7: リスクを判定する

PR 全体を `low` / `medium` / `high` の 3 段階で判定する。low-risk change として軽く通してよいかを決めるのが目的。

**まず変更の種類を分ける。** 1 つの PR に両方含まれるなら、それぞれ判定して高いほうを採る。

**既存機能の修正** — 壊れたときの影響の大きさと、それをテストが捕まえるかで判断する。

| 段階 | 目安 |
|---|---|
| low | 振る舞いが変わらない（リネーム、ログ、コメント、ドキュメント）か、変化が局所的で呼び出し元が限られ、変わった振る舞いをテストが直接検証している |
| medium | 呼び出し元が複数ある、共有モジュールに触れる、エラー経路・境界値が変わる、またはテストが変更後の振る舞いを直接検証していない |
| high | 公開 API・スキーマ・データ形式・設定の互換性が変わる、既存データの書き換えや再実行が絡む、権限・秘匿情報に触れる、ロールバックが難しい |

**新規機能の追加** — その後の方向性に影響するか（後から変えにくい決定を含むか）で判断する。

| 段階 | 目安 |
|---|---|
| low | 既存から独立していて、消しても他に影響しない。今後の実装がこれに依存しない |
| medium | 他の機能が今後これを使う前提になる（共有ユーティリティ、新しい規約・パターンの導入）が、後から差し替えられる |
| high | 公開 API・スキーマ・データ形式・ディレクトリ構成・技術選定など、一度入ると後続の設計を縛り、変更に移行コストがかかる決定を含む |

**CI/CD が pass していることは判断の根拠にしない。** テストが通ることと、変わった振る舞いが検証されていることは別。
テストの中身を読み、変更した振る舞いを実際にアサートしているかで判断する。テストが無い・薄いなら段階を上げる理由になる。

判定には必ず根拠を添える。どの観点で段階が決まったかを書く。

## 出力形式

```markdown
## 概要
（1 段落。何の機能の、何を、なぜ変えた PR か）

## リスク判定: low | medium | high
- 変更の種類: 既存機能の修正 / 新規機能の追加（両方ならそれぞれの段階）
- 根拠: 段階を決めた観点（影響範囲、互換性、後続設計への影響、テストが変更後の振る舞いを検証しているか）

## 変更対象の大元の機能
- 何のための機能か
- 呼び出し元 → この機能 → 呼び出し先（データの流れ）
- 変更対象の責務

## 変更の背景
（Issue・PR 説明・コミット・履歴から。事実と推測を区別）

## 何がどう変わったか
### <ファイル or 関数>
Before: ...
After: ...
振る舞いの差: ...

## コードレビュー
- **must** `path:line` — 指摘。理由。提案
- **should** ...
- **nit** ...
（PR 説明にない観点からの指摘にはその旨を書く。取捨選択で残らなければ「問題なし」と書く）

## レビューで見るべきポイント
（優先順に 3〜5 件。「どこを」「何を確認するか」「なぜ重要か」）
```

## 注意

- **PR 説明を検証対象として扱う。** 説明は書いた人の意図であって、実装の事実ではない
- **推測は推測と書く。** 「〜と思われる」「Issue には書かれていないが」を省かない
- **取捨選択で残らなければ「問題なし」と書く。** 落とした候補を復活させない。「見るべきポイント」は問題がなくても書く
- 差分が大きいときは、振る舞いが変わる箇所を先に、リネームや移動は後にまとめる
