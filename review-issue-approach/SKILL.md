# review-issue-approach

**方針を「正しいか」ではなく「もっと単純で良い道はないか」で読む。**

対象は PR の差分ではなく、PR が解こうとしている**親 Issue の方針**（何を解くために、何を作り、何を作らないと決めたか）。
目的は設計の考察。誤字・小さな矛盾・実装のバグは、方針の選択を変えるときだけ扱う。

複雑さは低いほど良い。複雑さは**払う価値**と**払い続けられるか**の両方が言えたときだけ残す。

**GitHub には 1 バイトも書かない。**

## Step 1: 材料を集める

PR 番号だけを渡されたら、カレントディレクトリのリポジトリを使う。

```bash
gh repo view --json nameWithOwner --jq .nameWithOwner
```

```bash
bash ~/.claude/skills/explain-pr/scripts/fetch_pr.sh OWNER/REPO#N
```

出力先ディレクトリが最後の行に出る。`pr.json`・`diff.patch`・`issue-N.json`（紐づく Issue、コメント込み）を使う。

**親 Issue** は `pr.json` の `closingIssuesReferences`、無ければ本文の `#N` で決まる Issue。
候補が複数で、どれが方針を持つか本文から決まらなければ、ユーザーに聞いて止まる。
候補が無ければ、その旨を伝えて止まる。PR 説明だけで方針を推測しない。

親 Issue がさらに上位の Issue（sub-issue の親）を持つなら、上位の目的と兄弟 Issue も取る。

```bash
gh api graphql -F owner=OWNER -F repo=REPO -F number=ISSUE -f query='
query($owner:String!,$repo:String!,$number:Int!){repository(owner:$owner,name:$repo){issue(number:$number){
  parent{number title body subIssues(first:50){nodes{number title state}}}}}}'
```

サンドボックスで `gh` のネットワークが落ちたら、その旨を伝えて止まる。

## Step 2: 方針を取り出す

親 Issue の本文とコメントから、次を書き出す。書かれていないものは「記載なし」とし、推測で埋めるなら推測と明記する。

- **解く問題**: 誰が何に困っているか
- **制約**: 期限、互換性、既存の決定、運用体制
- **採った方針**: 何を作るか、何を作らないか
- **検討した代替案**と**選んだ理由**

`diff.patch` は方針が実装でどれだけの量・概念になったかを測る材料として読む（Step 4）。差分のレビューはしない。

完了条件: 4 項目すべてに、Issue からの引用か「記載なし」が入っている。

## Step 3: 問題を言い直し、最小の解を置く

方針を見る前に、**解く問題だけ**から最も単純な解を 1 つ考える。既存の仕組みの流用、手作業、何もしない、も候補に入れる。

これが以降の物差しになる。方針がこの最小の解より複雑なら、その差分が評価対象。

## Step 4: 複雑さを判定する

方針が持ち込むものを数える。

- 新しい概念・用語、コンポーネント・層・抽象
- 設定・フラグ・分岐、状態の種類
- 外部依存、同期し続ける必要のある複数の置き場所
- 人が守る手順
- 一度入ると後から変えにくい決定（スキーマ、公開 API、データ形式、ディレクトリ構成、技術選定）

| 段階 | 目安 |
|---|---|
| 低 | 最小の解とほぼ同じ。新しい概念が無いか 1 つで、消しても他に影響しない |
| 中 | 最小の解より要素が多いが、どれも局所的で後から外せる |
| 高 | 新しい層・抽象・状態・手順を複数持ち込むか、後から変えにくい決定を含む |

持ち込むものそれぞれを**本質的な複雑さ**（問題そのものが要求する）と**偶有的な複雑さ**（方針の選び方から来る）に分ける。

## Step 5: 複雑さの値打ちを評価する（中・高のとき）

偶有的な複雑さの要素ごとに、2 つの軸で判断する。

- **払う価値**: 何を買っているか。それが無いと、誰が・いつ・何に困るか。その困りごとは今あるか、将来の想定か
- **払い続けられるか**: 次に読む人が理解できるか、運用者が手順を守れるか、変更のたびに何箇所を直すか、後から外せるか

| 判定 | 意味 |
|---|---|
| 価値あり・許容可 | 今ある困りごとを解き、維持もできる。残す |
| 価値あり・許容不可 | 困りごとは本物だが、この形では維持できない。同じ価値をより単純に得る方法を提案する |
| 価値薄・許容可 | 将来の想定のための先回り。今は外し、必要になってから足す方が安いかを示す |
| 価値薄・許容不可 | 外すよう提案する |

本質的な複雑さは判定しない。「問題が要求する」と 1 行添える。

## Step 6: 代替案を出す

最小の解（Step 3）と、Issue で検討された代替案を、採った方針と並べて比べる。代替案は 2〜3 個に絞る。

比べる軸: 複雑さ、解ける範囲、後からの変えやすさ、移行・運用の手間。

## Step 7: 提言を絞る

提言は方針の選択を変えるものに限る。重要なものから 3 件まで。
各提言は **何を変えるか + なぜ（誰が何に困る・何が楽になる） + 代償** の 3 点で書く。

方針が最小の解に近く、複雑さが低いなら「方針は妥当」と書いて提言は空でよい。良い方針を良いと言うことも報告の一部。

## 出力形式

```markdown
## 概要
（1 段落。どの Issue の、何を解く方針か。対象 PR はその方針のどの部分か）

## 方針の要約
- 解く問題:
- 制約:
- 採った方針:
- 検討した代替案と選んだ理由:
（上位 Issue があれば、その目的と兄弟 Issue の中での位置づけ）

## 評価
### 良い点
### 懸念
（方針の選択に関わるものだけ）

## 複雑さ: 低 | 中 | 高
- 最小の解: ...
- 方針が持ち込むもの: 要素ごとに 本質的 / 偶有的

## 複雑さの値打ち（中・高のとき）
| 要素 | 買っているもの | 払い続けるコスト | 判定 |
|---|---|---|---|

## 代替案
| 案 | 複雑さ | 解ける範囲 | 変えやすさ | 移行・運用 |
|---|---|---|---|---|

## 提言
1. **何を変えるか** — なぜ。代償

## 作者に聞きたいこと
（Issue に書かれておらず、評価を左右する前提。無ければ省く）
```

## 注意

- **Issue の記述は作者の意図であって、事実ではない。** 「〜のため必要」とあれば、その必要が今あるかを確かめる
- **推測は推測と書く。** 特に「記載なし」を埋めたところ
- 方針がすでに実装済み・マージ済みでも、より良い道があれば書く。そのときは今から変える代償も添える
